    Рабочий интерфейс настроек¶

    UI-REQ-026. Рабочий интерфейс настроек¶

    Для просмотра и изменения зарегистрированных бизнес-настроек используется отдельный рабочий интерфейс «Настройки» с точкой входа из раздела «Клуб» для пользователей, которым соответствующие операции разрешены серверной авторизацией. Сам факт видимости интерфейса не создаёт полномочия менять значение параметра.

    Интерфейс разделяет настройки по нормативным классам SET-REQ-001: системные настройки по умолчанию, сезонные параметры и версионируемые финансовые настройки. Эти классы не смешиваются в одну неразличимую таблицу, поскольку имеют разные правила применимости, действия во времени и требования к основанию.

    Список настроек, их типы и доступные действия не зашиваются в React-клиент отдельным перечнем ключей. Веб-клиент получает от серверной части каталог зарегистрированных настроек, доступных текущему пользователю. Для каждой настройки сервер передаёт как минимум стабильный ключ, человекочитаемое название и описание, класс настройки, тип значения и единицу измерения при наличии, текущее действующее значение, сведения о будущей версии при её наличии, возможность редактирования и требования к дополнительным полям изменения. Добавление новой зарегистрированной настройки или изменение её описания на сервере не требует отдельного изменения React-кода для появления её в общем интерфейсе.

    Для значений интерфейс использует типизированные элементы ввода вместо свободной строки там, где тип известен: число, денежная сумма, процент, дата, дата и время, количество дней и другие зарегистрированные типы. Клиентская проверка помогает пользователю, но окончательная допустимость значения, полномочия и бизнес-ограничения проверяются сервером.

    Для системной настройки по умолчанию карточка показывает текущее значение, дату начала его действия и, при наличии, запланированное будущее значение. Изменение выполняется созданием новой версии по SET-REQ-003 и SET-CASE-001; прежняя версия не перезаписывается.

    Для сезонного параметра пользователь сначала работает в контексте конкретного сезона. Интерфейс явно показывает выбранный сезон и значение именно этого сезона. Параметры завершённого сезона недоступны для обычного редактирования; изменение параметра одного сезона не должно визуально выглядеть как изменение глобального значения или других сезонов. Требования SET-REQ-005 и SET-CASE-002 сохраняются.

    Для финансовой настройки интерфейс показывает действующее значение, дату начала действия текущей версии и связанное решение-основание. При создании новой версии решение-основание и дата вступления значения в силу являются обязательными в случаях, предусмотренных FIN-REQ-029–FIN-REQ-033 и SET-CASE-003. Техническое право редактирования не должно визуально представляться как право самостоятельно принять финансовое решение.

    Перед сохранением изменения интерфейс показывает пользователю сводку: название настройки, прежнее значение, новое значение, дату начала действия и основание, если оно требуется. После успешного сохранения показывается новое состояние, полученное от сервера; оптимистическое отображение неподтверждённого значения как уже действующего не используется.

    Для каждой настройки доступна история версий в пределах полномочий пользователя. В истории показываются как минимум прежнее и новое значения, дата и время изменения, автор технического изменения, дата начала действия и основание при наличии, как требует SET-REQ-003. Будущие версии визуально отличаются от уже действующих.

    Интерфейс поддерживает поиск по названию и ключу настройки и фильтрацию по классу. Технический ключ показывается как дополнительная информация, а не вместо понятного человеку названия. Отсутствие доступных для изменения параметров не должно приводить к показу неработающих кнопок редактирования: пользователь видит только разрешённые действия, при этом сервер независимо проверяет каждую операцию.

    Этап: MVP

    UI-REQ-027. Метка развернутой версии¶

    В авторизованном веб-интерфейсе в футере мелким шрифтом отображаются дата и время начала production-деплоя текущей сборки и короткий хэш Git-коммита, из которого собран веб-интерфейс.

    Метка служит для оперативной проверки фактически развернутой версии и не является пользовательской версией продукта. Слово «опубликовано» и отдельный номер версии не требуются. Значения должны формироваться из метаданных production-деплоя, а не задаваться вручную в React-коде.

    Этап: MVP

    UI-REQ-028. Глобальный центр уведомлений¶

    В авторизованном веб-интерфейсе доступен глобальный центр уведомлений по правилам NOTIF-REQ-013 и NOTIF-REQ-014. Центр открывается из постоянной иконки в верхней панели и не является частью разделов «Мой клуб», «Катание», «Работы» или «Клуб».

    Числовой badge на иконке показывает только количество непрочитанных уведомлений. Если непрочитанных уведомлений нет, но существуют прочитанные сообщения с незавершённым обязательным подтверждением, интерфейс сохраняет отдельный ненумерованный признак требуемого внимания и не выдаёт такие сообщения за непрочитанные.

    Внутри центра уведомления группируются по пользовательскому приоритету: сначала сообщения с незавершённым обязательным подтверждением, затем непрочитанные обычные уведомления, затем история прочитанных и подтверждённых сообщений. Открытие центра само по себе не изменяет ни состояние прочтения, ни состояние подтверждения.

    Для уведомления показываются тема, понятный фрагмент содержания, дата и время, состояние прочтения, признак обязательного подтверждения при наличии, срок только если он задан профильным процессом, и понятный контекст связанного объекта при наличии.

    Открытие обычного уведомления показывает полное содержание и переводит его в прочитанное. Открытие уведомления с обязательным подтверждением также переводит его в прочитанное, но не создаёт подтверждение. Для такого сообщения доступно отдельное явное действие «Ознакомлен». После успешного подтверждения интерфейс показывает подтверждённое состояние и дату/время подтверждения, а сообщение остаётся в истории.

    Если уведомление связано с профильным объектом или действием, из него доступен переход в соответствующий сценарий. Отсутствие связанного объекта не делает уведомление неполноценным: его содержание должно быть доступно непосредственно в центре.

    На смартфоне центр должен поддерживать полноэкранное представление, удобное для чтения и подтверждения; на широком экране допустима компактная панель или оверлей. Для центра обязательны состояния loading, empty и error. Ошибка загрузки не должна визуально подменяться пустым списком, а неуспешное подтверждение не должно показываться как успешное до ответа сервера.

    Персональные внешние каналы не создают отдельные пользовательские центры уведомлений. При доступном и включённом канале он получает то же уведомление из общей серверной модели. В MVP привязанный Telegram поддерживает обычные уведомления и уведомления с обязательным подтверждением; подтверждение из Telegram должно немедленно отражаться в состоянии центра PWA. Email поддерживает доставку обычных и обязательных уведомлений на текущий подтверждённый основной адрес при включённой пользовательской настройке, но не предоставляет достоверного read-state и не позволяет фиксировать «Ознакомлен» непосредственно из письма. Отсутствие Telegram-привязки, email или отключённая email-рассылка не считаются ошибкой центра уведомлений.

    Этап: MVP

    UI-REQ-029. Рабочий интерфейс информационных кампаний¶

    Для пользователей, которым серверная авторизация предоставляет соответствующие полномочия, из раздела «Клуб» доступен рабочий интерфейс «Информационные кампании». Обычный получатель важного сообщения не должен заходить в этот интерфейс для чтения или подтверждения: предназначенное ему сообщение приходит через глобальный центр уведомлений и доступные привязанные внешние каналы по NOTIF-REQ-013–NOTIF-REQ-015.

    Рабочий интерфейс поддерживает полный жизненный цикл кампании по INFO-REQ-001: создание, запуск, контроль охвата, телефонный этап для оставшихся неподтвердивших, продление, просмотр завершённой кампании и переоткрытие при наличии соответствующего полномочия.

    Перед запуском интерфейс показывает важное сообщение, сформированную целевую аудиторию и её размер, текущий срок кампании и итоговую проверку параметров. Пользователь должен явно видеть, что при запуске фиксируется снимок аудитории по INFO-REQ-002. Интерфейс не определяет сам допустимость получателей и не заменяет серверные правила формирования аудитории.

    Карточка кампании показывает как минимум тему и текст сообщения, состояние, дату запуска, текущую дату окончания, общее количество получателей, количество и процент подтвердивших ознакомление, количество участников, которым информация доведена по телефону, общий охват и количество оставшихся неохваченными.

    Для кампании доступен список получателей с состоянием подтверждения, датой подтверждения при наличии, состоянием телефонного контакта и назначенным исполнителем при наличии. Список позволяет выделить актуальных неподтвердивших и другие нормативно значимые состояния, необходимые для сопровождения кампании.

    Для активной кампании пользователь с соответствующим полномочием может продлить срок по INFO-REQ-016; интерфейс показывает прежний и новый срок и требует причину. Для завершённой кампании переоткрытие по INFO-REQ-019 выполняется отдельным действием с новым сроком и не выглядит как редактирование завершённой записи. Прежние подтверждения и телефонные результаты не сбрасываются.

    Интерфейс отображает накопительную динамику подтверждений и исторический охват по INFO-REQ-013 и INFO-REQ-020. После завершения кампания остаётся доступной для просмотра сообщения, снимка аудитории, подтверждений, телефонного этапа, истории и аналитики.

    Телефонный этап использует только актуальный остаток неподтвердивших. Уполномоченный пользователь может распределить его между исполнителями автоматически поровну либо вручную по INFO-REQ-009. Исполнитель видит назначенных ему получателей и фиксирует только предусмотренные INFO-REQ-010 результаты. Перед контактом интерфейс учитывает актуальное confirmation-state общего уведомления; если участник уже подтвердил ознакомление через PWA или привязанный Telegram, звонок больше не показывается как необходимый.

    Результат телефонного контакта не отображается как подтверждение «Ознакомлен». Зачёт телефонной работы и перевод контактов в отработки отображаются только по серверному результату в соответствии с INFO-REQ-021 и связанными правилами WorkAccounting.

    Предупреждение о приближении окончания кампании по INFO-REQ-017 доставляется через общий механизм уведомлений и ведёт непосредственно в карточку кампании; отдельная параллельная система предупреждений в интерфейсе кампаний не создаётся.

    Для списка кампаний, карточки, получателей и телефонного этапа обязательны состояния loading, empty и error. Ошибки изменения срока, переоткрытия, распределения и фиксации контакта не должны оптимистически отображаться как успешные до подтверждения сервером.

    Этап: MVP
